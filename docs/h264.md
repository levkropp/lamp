# H.264 playback, checking and export

Windows source builds can now read selected H.264 Annex B and MP4/MOV files entirely through
assembly, decode their I/P/B pictures on the GPU, open a video-only window or export
packed NV12 frames. These are experimental command-line operations. The audio
library window remains separate; higher bit depths and audio/video
synchronization remain unfinished. [Main/High profile support](h264-profiles.md)
adds CABAC, weighted P prediction, 8×8 transforms and scaling matrices.
[B-picture support](h264-b.md) adds display-order output and bidirectional weights.
[Reference-picture support](h264-references.md) documents P pictures, non-IDR I
pictures and retained short/long-term references. [Presentation and controls](video-present.md)
document the SDR image path and video-only clock. [MP4/MOV integration](mp4-play.md)
uses the native demuxer and [timestamped packet frontend](h264-packets.md), with
file composition times and supported edit-list clipping.

```
lamp-cli.exe --video-check file.h264
lamp-cli.exe --video-play file.h264
lamp-cli.exe --video-decode file.h264 output.nv12
lamp-cli.exe --video-play movie.mp4
```

Use exactly one input and, for export, one new output path. These commands do not
accept the audio options. Output is headerless, cropped NV12: a Y plane followed
by interleaved UV for each picture in display order. The result line reports visible/coded widths
and heights and the picture count. For example:

```
video=h264 backend=d3d11 format=nv12 width=1920 height=1080 coded_width=1920 coded_height=1088 frames=4
```

`--video-check` runs the same GPU decode/readback without creating an output file.
It checks supported headers/framing and requests decoded images from the driver;
it is not an independent entropy-conformance validator. Drivers may conceal
corruption. Neither command opens an audio device or a video window.

## Supported boundary

- Byte-stream Annex B with three/four-byte start codes and leading/trailing zero
  bytes; one fixed SPS/PPS pair, with identical repeated parameter sets allowed.
- Clear AVC in [supported MP4/MOV layouts](mp4-video.md), including movie
  fragments, through one fixed AVC decoder configuration. The first enabled
  supported video track is selected; accompanying audio is skipped.
- Baseline/Main/High profiles 66/77/100, progressive 8-bit 4:2:0, **I/P pictures** including
  IDR and non-IDR I pictures. Up to 16 short/long-term references, sliding-window
  marking and adaptive operations 1–6 are supported. Main/High add CABAC and
  explicit P weights; High adds 8×8 transforms and SPS/PPS scaling lists. Main/High
  also accept [B pictures and reordered output](h264-b.md). Higher bit depths/chroma
  formats, transform bypass, fields/MBAFF, slice groups, redundant pictures and
  inferred missing pictures remain unsupported.
- POC types 0 and 2, frame-number/POC widths through 16 bits; SPS/PPS identifiers,
  QP/chroma/deblocking bounds and increasing macroblock slice starts are checked.
  Up to 256 contiguous slices are grouped into one picture. Dynamic parameter
  changes and additional parameter-set identities are not supported.
- Coded dimensions 16–4,096 in multiples of 16, subject to the adapter's limits.
  SPS cropping is applied to exported luma/chroma, including left/top crops.
- VUI SAR, range, color and timing fields are parsed; bounded HRD structures are
  consumed. The video window uses SAR and SDR color; Annex B uses nominal timing,
  while MP4/MOV uses composition timestamps and supported edits;
  HDR and SEI timing remain unimplemented. SEI/AUD/filler/end NAL units are
  skipped; SEI timing is not applied.

The [Direct3D backend](windows-video.md) selects the default hardware adapter's
unencrypted H.264 VLD/NV12 short-slice configuration. There is no software fallback
or alternate-adapter selection yet. Its surface-pool limit and actual compressed
buffer capacities also apply. Matroska and other container video remains
unfinished. MP4/MOV video commands remain separate from audio playback.

## Bounds and failure handling

The original shared frontend uses a **16,384-byte** caller-owned context. One
16 MiB compressed-frame address range is reserved lazily, committed in 64 KiB
increments and reused. Parameter sets are bounded to 4 KiB each; completed frames
include 128-byte zero padding and must fit both the frontend and driver buffers.
Exp-Golomb readers are bounded, header emulation-prevention bytes and parameter-set
trailing bits are checked, and all byte accesses stay inside the supplied input.
The caller retains the input mapping until close; close frees scratch storage and
clears the context. Only one owner accesses each context.

`h264_open(context, bytes, size, cancel_pointer)` initializes a new/closed context.
`h264_next(context)` returns 1 with the native submission at `HP_DESC`, 0 at EOF,
or -1 with a sticky error. `h264_close(context)` is idempotent. The layout is in
`src/h264.inc`; metadata and packet pointers remain valid until the next call or
close. An optional cancellation DWORD is checked before work and every 4 KiB of
NAL scanning. This is a frame producer, not a seeking index or worker queue.

The CLI preflights the whole file's supported framing/headers before creating an
output. Export uses `CREATE_NEW` and preserves existing files, including an input
used as the requested output. On a handled failure or cancellation, it closes and
removes only the partial output created by that invocation. Ctrl+C sets the
cancellation flag. Busy GPU begin/readback operations use bounded five-second
retry deadlines; individual driver calls are not promised to be interruptible.

Both Windows executables now link the assembly video modules and import the
normal Windows `d3d11.dll`. The video commands create the D3D device; the audio
commands retain their existing path. No C runtime, codec DLL, FFmpeg subprocess
or test-language interpreter is linked into the player.

## Recorded IDR verification

The earlier IDR-only [Windows report](../reports/h264-file-windows-verification.json) records 20
encoded files and **115 GPU-decoded pictures**, with all **64,813,440 exported
NV12 bytes** equal to FFmpeg 8.0.1 references. Coverage includes six coded sizes
through 1920×1088, 1920×1080 cropping, four-sided cropping, 2/4/8 slices, POC type
0, mixed start-code lengths, leading/trailing zeros, repeated headers, SAR/color
tags, AUDs, Unicode paths and packets spanning multiple commit increments. An
i7-12700KF / RTX 5070 Ti with driver 32.0.16.1692 ran these checks. The exact
encoder executable and generated inputs/reference outputs are hash-pinned.

Windows and [Linux](../reports/h264-file-linux-verification.json) produce identical
packet bytes for all 20 files. Six files also equal the previous independent
test-only Python header oracle exactly. Each host passes **41,614,136 guarded
checks / 3,075 opens**, including 1,025 protected prefixes, 2,048 deterministic
mutations, cancellation and reopen; the mutation fingerprint matches across
hosts. Mutated/synthetic inputs are exercised only by the CPU frontend and are
never submitted to the GPU. Nineteen synthetic cases check metadata, 256/257
slice limits, unsupported features and malformed headers. The historical corpus
rejected B pictures before their extension; current regression negatives use
High10 and 4:2:2 profiles and reject without creating exports.

Native commands also preserve an existing export and an aliased input. Two
isolated test-only CLI objects set cancellation or a short-write report after one
real exported frame; both remove their owned partial output. They do not alter
shipping code or simulate physical console events. The previous published binary
lacks the video result, providing a negative control. Existing Windows/Linux
six-format audio smoke checks pass, Windows imports/resources pass, and the
[shared parser translates/assembles for ARM64 macOS](../reports/h264-file-mac-assembly-verification.json).
Native Mac execution and Linux/Mac GPU decoding are not established.

To reproduce, build first, then generate the corpus on a host with FFmpeg/x264:

```
python tests/verify-h264-file.py --bin bin/h264-file-check --generate --controls
python3 tests/verify-h264-file.py --bin build/h264-file-check
```

Both hosts can share `--fixtures PATH`. Test controls need LLVM on PATH or the
documented local WSL toolchain. These are correctness/component checks, not
playback CPU, GPU, latency, power or dropped-frame measurements. Frame seeking,
other container video readers and connection to
the [audio-master scheduler](video-sync.md) remain milestone 4 work.

The parser is original assembly based on [ITU-T H.264 (08/2024)](https://www.itu.int/rec/T-REC-H.264-202408-S/en).
The native metadata layout follows the Windows SDK and the sources recorded in
the [hardware backend notes](windows-video.md). C/Python and FFmpeg are test-only.

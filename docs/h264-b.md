# H.264 B pictures and display order

Windows source builds accept progressive 8-bit 4:2:0 Main/High B pictures through
[`--video-play`, `--video-check` and `--video-decode`](h264.md). Baseline remains
I/P only. All three commands retain pictures and return them in display order.
The video-only window keeps its nominal frame clock, pause, single-picture
stepping, resize and replay controls. Container timestamps, the real audio-master
clock, accurate seeking and the other [milestone 4 gates](../ROADMAP.md#4--video-and-synchronization)
remain unfinished.

## Parsing and output ownership

The assembly slice reader handles B spatial/temporal direct prediction, both
reference lists and their modifications, per-slice active counts up to 16 per
list, CABAC/CAVLC, and unweighted, implicit or explicit bidirectional weights.
Explicit luma/chroma denominators and signed weights/offsets retain the existing
checked bounds. Compressed slices and DXVA metadata go directly to D3D11; no
software codec, external codec library or FFmpeg process enters the runtime.

The SPS reader validates VUI `max_num_reorder_frames` and
`max_dec_frame_buffering` against the reference count and the level's
`MaxDpbFrames` bound. Absent values follow H.264 E.2.1; the level table follows
Table A-1, including level 1b. This does not implement every level/HRD conformance
check or SEI picture-timing presentation.

`src/win/video_stream.s` adds a fixed 512-byte, single-owner bridge between the
16,384-byte parser and hardware decoder. At most 17 output records retain
`{epoch, POC, surface}`; the bridge chooses the smallest signed POC once the
declared reorder bound is exceeded, or drains at EOF. IDR/MMCO5 boundaries flush
older output before decoding the new epoch. An IDR's
`no_output_of_prior_pics_flag` discards queued prior pictures when requested.
Duplicate or late POC within an epoch fails rather than silently reordering an
already-returned picture.

Queued pictures and the last returned picture pin their GPU surfaces. Reference
marking and free-slot selection exclude those pins. The last output stays
available for pause, repaint, resize and EOF until its successor is selected.
The caller must finish readback or the presenter's GPU fence before requesting
the next picture. Pending GPU work retries the same parsed picture without
duplicating decode or output. Errors and cancellation stick until close.

The requested pool is `max(max_dec_frame_buffering, 1) + 2`, at most 18 surfaces;
a driver may require more, up to the existing 32-surface cap. Existing 128 MiB
decoder/staging and presenter allocation limits still apply. Unsupported resource
requirements fail cleanly. Successful surfaces retained for output remain
selectable across an IDR even though decoder reference validity resets.

## Verification

On Windows 11, using the RTX 5070 Ti hardware adapter:

- **1,074 images / 154,151,640 NV12 bytes** exactly match independent FFmpeg
  decoding across 13 encoded sequences. They include 1/3/8 configured B pictures,
  B-pyramid normal/strict, spatial/temporal direct, Main/High, CABAC/CAVLC,
  unweighted/implicit/explicit B weights, 16 references, four slices, open GOPs,
  crop/SAR/full range, IDR transitions, POC wrap and 720p.
- The explicit-weight input changes headers of genuine encoded CAVLC pictures,
  retaining compressed payload bits. Independent decoding supplies the changed
  pixel reference. Synthetic coefficient bodies never reach a driver.
- Windows and Linux each pass 30 syntax/default/boundary cases and 51,721,632
  guarded checks across 3,075 opens. Packet bytes and mutation fingerprints agree.
- A CPU-only stream model checks 544 bounded random permutations, retry
  ownership, epoch flush/discard, sticky failures and cancellation. Five isolated
  broken objects prove the checks catch lost pins, reversed order, unwanted
  discard, leaked prior output and mishandled busy decode.
- Main and High B-frame GPU presentation each check 43 rendered images, 3,225
  sampled RGB channels, crop/aspect/range/matrix and black letterboxing. Each runs
  a real 90-picture sequence through hidden-window pause, steps, final-frame EOF,
  resize, minimize, replay, cancellation and close. These are owned hidden
  windows; they do not establish visible-display latency or performance.

The earlier 506-image Main/High, 626-image reference-picture and 115-image IDR
corpora remain regressions. Shared frontend translation and assembly for Apple
Silicon are checked separately; native Mac execution and Mac/Linux video
presentation remain unverified.

Run the new corpus on Windows with FFmpeg/x264 and the normal test C compiler:

```powershell
python tests/verify-h264-b.py --bin bin/h264-b-check --generate --controls
python tests/verify-video-present.py --bin bin/h264-b-check --profile high --references --bframes 3 --report bin/h264-b-check/b-video-present-verification.json
```

The Linux invocation of `verify-h264-b.py` checks shared parsing and packet
serialization only. Reports retain exact source, executable, fixture and output
hashes. These checks establish the stated profile subset, rather than universal
H.264 support. Higher bit depth/chroma formats, fields/MBAFF, POC type 1, changing
parameter sets and inferred missing pictures remain unsupported.
